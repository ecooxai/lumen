# Rendered-app WPT validation

`full_runner.py` runs upstream `testharness` tests in the actual native Lumen
desktop executable and in an isolated Chromium/Chrome process. It does not use
the older `jsrun` executable as a substitute for the browser.

## Scope and evidence

Use the complete upstream WPT checkout and the manifest generated by its own
`wpt manifest` command. The inventory preserves generated worker wrappers, URL
query variants, test types, source-file counts and the exact upstream revision.
Tests are loaded as top-level documents from the official WPT server. Upstream
test files and assertions are not rewritten.

The currently implemented execution adapter is `testharness`. Reference tests,
WebDriver protocol tests, manual tests and other classes remain explicitly
`NOTRUN` when the complete manifest is scheduled. The JavaScript reporter does
not implement `testdriver` automation. Results from tests that require such
automation must be interpreted with that limitation; API conformance cannot be
inferred from an automation failure.

The default run schedules all manifest test URLs. `--types`, `--prefix` or
`--limit` create a subset. A subset must never be described as the full suite.
`run.json` records the complete inventory counts and whether the schedule is
complete. A complete schedule containing `NOTRUN` entries is not a completed
full-suite execution.

## Mac setup

Run commands on the authorized Mac, not on a substitute local VM. This adapter
rejects non-macOS execution. Use Python 3.12 for this checkout; Python 3.15 has
removed the CGI server class used by the upstream server.

Create the upstream Python environment, install the upstream command's required
dependencies, then generate the manifest using the command's own `--help` for
the checked-out revision. Start `wpt serve` from the upstream checkout so its
resource and certificate paths resolve correctly.

Preserve the official `web-platform.test` and `not-web-platform.test` origins.
The upstream-generated hosts file is one option. Lumen's test-only
`LUMEN_HOST_MAP` and Chromium's `--host-resolver-rules` can instead direct those
same names to the local server. Record effective server ports and configuration.

For HTTPS, Lumen accepts the upstream CA through `SSL_CERT_FILE`. Chromium can
use the exact upstream test certificate's SPKI hash with
`--ignore-certificate-errors-spki-list`. Do not use a global certificate bypass
and then claim TLS validation coverage. All trust overrides are confined to the
test process. Do not import or expose users' real session cookies.

## Commands

From the Lumen repository, after the official manifest/server are ready:

```sh
python3.12 tests/wpt/full_runner.py inventory \
  --wpt-root output/wpt/upstream \
  --output output/wpt/inventory.json

python3.12 -m unittest discover -s tests/wpt -p test_full_runner.py -v
```

Run a short paired infrastructure preflight using identical selection, origins,
and timeouts. Confirm a known assertion completes through both adapters before
the broad run. Native Lumen uses a fresh temporary profile/download directory
per case; Chromium uses a dedicated temporary browser profile and a fresh
browser context per case. Neither adapter consumes a signed-in user profile.

For a full scheduled run, omit all selection filters:

```sh
python3.12 tests/wpt/full_runner.py run \
  --inventory output/wpt/inventory.json --engine lumen \
  --binary build/lumen --output output/wpt/lumen-full
```

Launch the matching Chromium run with `--engine chromium`, the actual installed
browser binary, a separate output directory, and the required process-specific
host/certificate arguments. `--chromium-arg` can be repeated. Do not run both
engines concurrently on a loaded host and call their resource numbers a
controlled performance comparison.

An interrupted run resumes with the same arguments plus `--resume`. The runner
checks test revision, manifest, exact schedule, browser binary, reporter source,
runner source, origins, and timeout budgets. A changed executable or harness
requires a new output directory. Three consecutive infrastructure failures stop
at a checkpoint, leaving remaining files unrun instead of assigning invented
browser failures to the entire remaining suite.

```sh
python3.12 tests/wpt/full_runner.py compare \
  --lumen output/wpt/lumen-full \
  --chromium output/wpt/chromium-full \
  --output output/wpt/comparison.json
```

## Reading results

- `results.jsonl`: one record per scheduled outcome, including exact URL,
  subtest names, statuses, error messages, timings and available telemetry.
- `summary.json`: checkpointed totals with explicit timeouts, crashes,
  infrastructure failures, `NOTRUN` files and remaining files.
- `run.json` and `schedule.json`: provenance and the exact denominator.
- Case console logs and one-second process-tree metric logs: diagnostic evidence.

The headline **file pass rate** is files whose harness and every assertion pass,
divided by attempted files. Timeouts, crashes, errors and infrastructure failures
remain in that denominator. A testharness file with zero assertions is not a
passing file. A secondary completed-only metric is explicitly labelled and must
not hide unsuccessful attempts.

The **subtest pass rate** is passing recorded assertions divided by recorded
assertions excluding `NOTRUN`; all other statuses are shown separately. Missing
assertions cannot be assumed to have passed.

**Chromium-pass retention** matches exact test URLs and assertion names. Its
denominator is Chromium's passing assertions in the identical schedule. Missing
or failing Lumen assertions count against retention. Chromium files not yet run
remain visible, so this metric cannot establish unmeasured full-suite parity.

CPU samples initially use the repository monitor's labelled `ps` process CPU
metric. RSS is the sum of the selected process tree's resident sets; shared pages
can be counted more than once. Very short cases can finish before a useful
sample exists. This is missing telemetry, not a functional test failure.
