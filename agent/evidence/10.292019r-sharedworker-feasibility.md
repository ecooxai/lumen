# SharedWorker feasibility assessment

Recorded 2026-10-29 by GPT-6 Astra Pro, built-in Apple/performance agent. This is a read-only assessment of the current C/V8 implementation, not an implementation or a conformance result.

## Assessment

A real implementation can reuse the existing worker isolate, native asynchronous networking, serializer and event-loop machinery. It cannot obtain correct multiple-client lifetime or message routing merely by exposing another JavaScript constructor. A separate, bounded candidate is reasonable; a full SharedWorker conformance claim within a 45-minute implementation window would be unsupported. Preserve the tested native candidate while qualifying the new path.

The main ownership changes are concrete:

- `src/js/worker.cc` stores one raw `JsCtx *owner` per `Worker`. `workers_pump` swaps a single outgoing queue for that owner, and `workers_kill` terminates the entire worker when that one document dies. Shared workers need a native registry and a set of live client owners, with per-client output routing. Disconnecting one client must leave others operating; final owner removal must cancel outstanding native requests and free the isolate/queues under the selected bounded lifetime policy.
- Existing worker and window `MessagePort` implementations in `worker.cc` and `prelude/07b-net.js` use per-realm integer IDs. `start()` is currently a no-op and `close()` only severs a JavaScript `_other` link. The shared path needs globally unique native endpoint identities, queued delivery before start, native close/disentangle, transfer ownership, and cleanup of remote port maps. Reusing numeric IDs from separate realms would permit collisions.
- `js_bus_post` in `src/js/jsnative.cc` retains only five seconds or 256 messages. This BroadcastChannel/localStorage bus cannot serve as a reliable MessagePort transport. A blocked or not-yet-started port must not silently lose a burst exceeding that retention policy.
- Typed native connect/disconnect/message queues should carry client identity independently of user-controlled message data. Worker callbacks and V8 handles must remain on the worker's own thread. Existing native request finalizers already support that requirement.

## Observable acceptance gates

Use at least two separate real document contexts, not two wrappers in one realm. Prove one actual isolate/shared global counter and a single script load for a matching worker, with distinct reply ports and no cross-delivery. Destroy the first document and continue using the second. Destroy the last owner with a real held HTTP request; verify socket cancellation, zero pending native ownership, isolate completion and bounded thread/RSS recovery.

Also require a `connect` event whose `source` equals `ports[0]`, correct `SharedWorkerGlobalScope` identity and absence of dedicated-only globals, message queuing before `start()` or `onmessage`, FIFO delivery of more than 256 messages, close suppression, transferred ArrayBuffer detachment, real transferred MessagePort routing, and rejection/error behavior for origin/CSP/options mismatches. A parent event-loop stall must not stop worker networking or timers. Constructor failures and script-load failures must free incomplete registry entries.

## Normative details to preserve

The current HTML algorithm matches a constructor storage key, constructor URL and worker name. Once a worker matches, incompatible type, credentials or extended-lifetime options cause an error instead of creating an independently keyed worker. Storage partitioning and opaque-origin creation require explicit treatment. A name-only or origin-only cache is insufficient. The project should confirm its pinned WPT expectations and Chrome control where older tutorial text differs from the current algorithm.
